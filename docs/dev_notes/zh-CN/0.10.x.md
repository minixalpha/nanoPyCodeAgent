### 开发前先固定 0.9.0 的 20 题 baseline

0.9.0 发布后，于 2026-10-05 重新完整运行原来的 Terminal-Bench 2.1 pilot20，
作为 0.10.0 开发前的起点。Agent 和 Harbor adapter 都固定到发布提交
`c0605369d277352ac0d5ec20d02017b7cb149314`；预检和四组正式运行的 wheel 均与 PyPI
0.9.0 发布包的 SHA256 一致。运行期间没有改动 agent 或 harness 源码。

使用 DeepSeek 官方 Anthropic 兼容端点、`deepseek-flash`、100 回合和每次请求
65,536 输出 token 上限。每题工作预算仍为原始 agent 时限减 180 秒；标准入口按
720、1,620、2,220、3,420 秒分成四组，合计 20 题，每题只运行一次，组内并发为 2。
依赖安装时限明确从历史默认 360 秒调到 1,800 秒，不占用题目的工作预算，原始
逐次 verifier 时限保持不变。

先做 install-only：20 题 agent 安装全部通过；QEMU 已注册的 verifier 依赖
profile 通过，其余 19 题明确记录为 `not_configured`。任务镜像、APT 源和官方
测试保持原样，缓存命中按原索引的文件名、大小和 SHA256 校验。

最终结果是 **18/20 通过、2 题评分失败、0 题未评分**。两道评分失败为
`model-extraction-relu-logits`（缺少要求的脚本和输出文件）与
`schemelike-metacircular-eval`（63 个子例通过 58 个）。两题的原生终态均为
`response_truncated`，但终态本身不能证明全部错误都由截断导致。所有原生
trajectory 均通过 ATIF 校验，保留所有试次，没有用重跑替换失败分数。

已知 token 费用估算小计为 **$1.974266**。Scheme 任务有两次已恢复的模型流
中断，其 usage 缺失，因此 token 总数和费用都不完整，不能把缺失部分当作零，也
不能把估算小计当成实际账单。

### 实验：一次截断后允许在原预算内继续

第一项实验只改变 headless run 对 `max_tokens` 的处理：每次 run 最多自动恢复
一次，沿用原始截止时间、回合计数和单次 token 上限。截断回复仍计入预算并保留
usage、费用和原始日志；它的工具调用全部跳过，不完整的 thinking 不进入后续
请求。恢复提示要求模型从已确认的工具结果和当前文件继续，不重放先前已执行的
工具。第二次截断仍停止，交互模式仍等待用户输入。

恢复提示沿用 schema v4 的 `input.injected`，reason 为 `truncation_recovery`，
可在 Journal 和 ATIF 中区分“发生过截断”与“实际启动过恢复”。正常工具执行或
传输重试不会重置恢复额度。

于 2026-10-05 固定提交 `e1be6ed1f81a17d73677b414d4d913adb81e9e25`，对原来两道
失败题各做一次全新运行。模型、100 回合、65,536 token、720/2,220 秒工作预算、
1,800 秒安装时限及官方逐次验证时限均保持不变。两题安装预检通过，verifier
依赖 profile 均明确为 `not_configured`。预检与正式运行的 wheel 完全一致，
任务镜像与完整任务 checksum 均与发布基线一致。

| 题目 | 本轮结果 | 截断次数 | 恢复次数 |
| --- | --- | ---: | ---: |
| `model-extraction-relu-logits` | 通过；约 362 秒，25 次模型回复 | 0 | 0 |
| `schemelike-metacircular-eval` | 通过，63/63 子例；约 1,399 秒，60 次模型回复 | 0 | 0 |

两题官方 verifier 均第一次完成，0 题未评分。token 记录完整，费用估算合计
**$0.235099**，仍不是 provider 实际账单。**两题都没有触发恢复，因此不能把
这次通过归因于新策略，也不能把原来的 18/20 改写成 20/20。** 本轮是不同模型
生成与不同并发配对下的两次新样本，没有重放原失败响应的确定性对照。

确定性测试覆盖了恢复后继续执行工具直至完成、第二次截断停止、传输重试期间
不重复注入、不重放已完成工具、不执行截断工具，以及截止时间、最后回合和
usage/费用累计。锁定依赖时核心测试 351 通过、4 项可选传输测试跳过；SDK 1.5.0
下 355 项通过；Harbor 兼容性与流程检查 91 项通过。机制的正确性已有测试覆盖，
真实截断任务上的收益仍未得到本轮实验证明。

### 追加实验：两题各运行三次，观察真实截断恢复

维护者随后明确要求两道题各追加三次全新运行。先提交固定六个 job 和队列顺序的
实验计划，再于 2026-10-05 14:27:47–15:20:14 UTC 执行，最多同时运行两题。
运行提交为 `382cb38413d7d5368ad1be97e85142f280172a5b`；21 个 agent/adapter
Python 文件与前轮实验完全一致，本轮没有修改运行逻辑。模型、任务版本、镜像、
100 回合、65,536 token、720/2,220 秒工作预算和逐次 verifier 时限均保持不变。

两题安装预检通过，verifier 依赖 profile 均为 `not_configured`。预检及六次正式
运行的 wheel 完全一致，73 个任务文件哈希保持不变，任务 checksum 与发布基线
一致。六次原生 ATIF 全部有效，官方 verifier 均第一次完成，没有未评分试次。

| 题目 | 第 1 次 | 第 2 次 | 第 3 次 | 截断 / 恢复 |
| --- | --- | --- | --- | --- |
| 模型提取 | 失败：权重行 2、27 未匹配 | 失败：权重行 24 未匹配 | 通过 | 1 / 1，发生在第 2 次运行 |
| Scheme | 通过，63/63 | 通过，63/63 | 通过，63/63 | 0 / 0 |

本轮合计 **4/6 通过、2 次评分失败、0 次未评分**；模型提取 1/3，Scheme 3/3。
完整 token 费用估算为 **$0.906352500**，不是实际账单；没有 usage 缺失的模型流。
所有原生终态均为 `completed`，说明正常结束本身并不等于解答通过官方验证。

模型提取第 2 次重现了基线的关键情形：第二次模型回复耗尽 65,536 token，尚未
创建脚本。约 326.302 秒时注入一次恢复提示，原 720 秒预算还剩约 393.698 秒。
随后又完成 15 次模型回复和 14 次工具执行，写出并修改 `/app/steal.py`、运行
本地检查，最终于约 552.428 秒主动完成，没有再次截断，也没有增加原预算。

官方验证执行脚本并找到了输出文件，但只恢复出 30 个神经元中的 29 个，权重行
24 未匹配，reward 仍为 0。**这次真实运行证明了截断后能够继续做有效工作，但
尚未证明能把失败救成通过。** 另一次模型提取失败没有发生截断，脚本和输出也
存在，只是有两行未匹配；官方测试会把可见的 20 神经元示例替换为 30 神经元网络，
因此仅验证可见示例不足以确认提取完整性。这提示后续可单独研究验证覆盖与算法
完整性，但本轮没有确定全部失败的算法根因。

保留全部六次结果，先前的 2/2 样本及 0.9.0 的 18/20 baseline 均不改写。三次
Scheme 都没有截断，仍不能据此判断恢复逻辑能否救回 Scheme；也不能从这批小
样本、不同生成路径与并发配对推导策略对通过率的因果提升。按预定次数结束，
没有看到结果后再追加试次。

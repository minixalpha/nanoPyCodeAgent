## 六题失败的原因

步骤引用为本地保留轨迹中的 ATIF `step_id`。结果 JSON 通过 SHA256 绑定这些
文件及官方输出。

| 任务 | 观察到的失败 | 验证启示 |
| --- | --- | --- |
| adaptive-rejection-sampler | 未提交 `/app/ars.R`。安装延迟和模型流中断耗尽 720 秒工作预算。 | 尽早产出最小交付物；限制安装和恢复工作。本次不能为已提交 ARS 算法提供任何证据。 |
| db-wal-recovery | 打开原始 SQLite 数据库，在备份前丢弃了加密 WAL。猜测值遗漏 WAL 更新。 | 有状态读取前保留全部输入和 sidecar；根据原始证据验证恢复值。 |
| kv-store-grpc | `SetValRequest` 使用 `val`；任务要求 `value`。自测客户端使用同一错误 schema。 | 从规范独立导出 API 契约。内部一致不能证明接口合规。 |
| query-optimize | 输出正确，但相对官方优化参考，查询过慢。 | 正确性确立后，建立可重复的目标运行时测量，测试候选查询计划。 |
| torch-pipeline-parallelism | 层调用缺少必需的旋转位置嵌入。真实自测在临近期限时发现错误。 | 尽早用微型前向/反向传播测试已安装 API；传递进程失败，并留出修复时间。 |
| regex-chess | 白王已被将军时仍允许王车易位。 | 在随机差分测试之外，为每个特殊规则前提补充明确的负例。 |

### 采样器：执行中断后缺少输出

第 5、9、13 步的安装调用均达到 bash 超时，包括尝试启动后台工作的调用。第 15
步时 R 已可用，此时工作预算已过去约 6.5 分钟。接下来两次模型调用分别约 241
秒和 29 秒后以 `RemoteProtocolError` 结束；最后一次调用又经过 58 秒达到期限。
没有完成任何实现写入。

九项官方测试全部运行，并因缺少文件失败。这是具有操作性原因的计分失败，
不是设置失败，也未证明算法错误。登记的预检未覆盖 R 安装。

### WAL 恢复：必须先保留证据，再检查

第 5 步并发检查部分 WAL 并打开原始数据库。SQLite 丢弃了无效的加密 WAL。第 7
步备份/解码已太晚。最终 JSON 包含 11 条看似合理的水果记录，值遵循 `id * 100`，
形状/计数检查通过。两项官方测试发现错误值，包括 id 1 应恢复为 `150`，实际
却为 `100`。第 53 步最终消息披露了 WAL 丢失及推断；并非未披露地声称恢复成功。

### gRPC：独立消费者本可发现不匹配

第 7 步定义 `SetValRequest.val`。第 9、13、23、37 步测试使用生成的客户端及
相同字段。测试覆盖真实 RPC、覆盖写、独立键、空键和整数边界，却从未构造任务
规定的请求。官方使用 `value=999` 和 `value=42` 的调用在到达服务器前就失败。
Descriptor 断言或独立定义的客户端能填补实际缺口。

### SQL：性能任务仅结果正确还不够

Verifier 测得参考中位数 **0.291814 秒**，解法中位数 **0.371624 秒**，约慢 27.35%；
允许倍数为 1.05。Agent 确实证明了 500 行输出精确一致，且保留原数据库，仅在
副本上建索引取得参考输出。第 33 步尝试重复计时的命令因缺少 `/usr/bin/time`
失败。后来的 shell 计时约 0.48 秒，相比慢得多的原查询显得不错。

优化参考和精确阈值对 agent 隐藏。可采取行动的缺口是可靠的比较性性能工作和
优化余量，而非期待 agent 知道隐藏参考。

### 流水线并行：验证开始太晚

第 11 步在 PyTorch/Transformers 可用前就写了实现。第 27 步编写的首次实质性
测试在参考测试 hook 中失败。修复该 hook 后，第 31 步在 attention 解包
`position_embeddings` 时暴露 `TypeError: cannot unpack non-iterable NoneType object`。
修复前期限已到。

两个官方 world-size 测试均进入提交代码，并因同一错误失败；两项结构检查通过。
这不是 verifier 安装错误。自测命令还将输出通过管道传给 `tail`，掩盖了失败
进程的退出状态。早期冒烟测试、明确进程状态和有界分布式测试可以更有效地使用
剩余预算。

### 正则表达式国际象棋：大量测试遗漏了特定负面条件

两局官方棋局发现白王在 e1 已被将军时仍多出王翼易位：一次由 e8 的车将军，
另一次由 d3 的马将军。其他棋局测试集和规则大小检查通过。

第 107、115、117 步修改易位生成和攻击过滤顺序。中间 X0 到 X1 状态仍在第一道
过滤前生成，因此即便初始王位被攻击，也能存活。后续易位状态因而可能逃过
最初的将军检查。

最终实现针对 `python-chess` 做了实质性的独立验证：最后修改后，一组 618 个
采样局面和另一组 600 个局面均通过，提供的检查脚本也通过。这些计数不代表
独立不重复局面或完整规则覆盖。需要明确覆盖在被将军、经过被攻击格和进入
被攻击格时易位的例子；最终声称三者均已排除，超出了证据。

不含依赖预检。累加 agent 工作为 321.38 分钟，agent 安装为 32.96 分钟，verifier

试验的用量/费用记录不完整；缺失调用未按零计价。

[此前的十二题基线](dev12-main-baseline-20261011.md)使用同一 main 提交，取得

变为失败，WAL 恢复两次均失败。试验随机性和传输/环境历史不同；这不能作为
agent 代码改进或回归的证据。

34 题池仍适合开发：保留全部 28 项通过任务作为回归检查，用六项失败做诊断。
Agent 实验应在相同登记条件下进行匹配的基线/候选重复运行，分别测量任务通过
率、验证证据、时间和信息接触。一次通过不能证明任务稳定性。剩余 55 个未打开
任务应保留到候选确定后，进行另一次预先声明的评估。

这些证据建议的下一步 agent 改动为输入保留、独立契约检查、尽早执行小测试、
可靠的退出/错误报告、针对性负例和可重复性能测量。这些是后续实验的假设；
本次运行均未应用。

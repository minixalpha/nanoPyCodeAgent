## 计分失败与 verifier 错误证据

- `db-wal-recovery`：保留混淆 WAL 前先打开原始 SQLite 数据库。Agent 报告 SQLite 删除了 WAL，随后推测缺失记录。官方测试发现 WAL 更新缺失：5 项通过、2 项失败。
- `torch-pipeline-parallelism`：两个 world-size 用例均因 `model.rotary_emb.fwd` 的 microbatch 数量不匹配失败。存在性和无 hooks 检查通过。第一次 verifier 尝试在依赖准备阶段超时；第二次执行全部四个用例。
- `dna-assembly`：提交的引物在 BsaI 识别位点前缺少要求的核苷酸 clamp，官方引物测试失败。
- `regex-chess`：提交的正则流水线允许王移入被马攻击的格子。官方两项通过、两项失败。本轮实际提交了 `re.json`；这是实现的计分失败，与此前六题重跑中仅因截断而未提交文件的情况不同。
- `build-pov-ray`：因缺少 `file_id.diz`，官方源码发行包检查失败。可执行文件和渲染检查通过；记录的 SSIM 为 0.8731。Agent 从官方 2.2 归档 URL 下载源码。仅凭标记文件缺失，不能认定实际构建的是其他版本。
- `multi-source-data-merger`：verifier 在 pytest 启动前因网络超时无法下载或解压 `pyarrow==22.0.0`。原生零分保留，分析分数为空。此次尝试已结束，并非 verifier 进程达到时限，因此未重试。
- `pytorch-model-cli`：APT 报告依赖不满足后，官方 pytest 在导入 cv2 时因缺少 `libGL.so.1` 而收集失败。Agent 此前使用 `dpkg --force-all` 强制安装编译器和开发包，留下依赖问题；agent 的环境修改促成了此次验证失败。未执行任何断言。原生零分保留，分析分数为空；CLI 正确性仍未验证。
- `pytorch-model-recovery`：三次原始 900 秒 verifier 尝试均在 pytest 启动前下载 PyTorch/CUDA 依赖时超时，始终复用同一输出。原生 `VerifierTimeoutError` 没有奖励，分析分数为空。

## 执行与完整性

全部任务修订、原始镜像身份、资源、包源、官方 verifier 脚本和逐次时限均与登记的开发池一致。每个已安装 wheel 均与记录的源码快照匹配。限制仍为 100 次模型回复、每次最多 65,536 个输出 token、原始任务 agent 时限减 180 秒的工作预算，以及独立的 1,800 秒安装时限。温度和 reasoning effort 均未设置。

新的安装预检共保留 35 次尝试，得到 **34 次成功、1 次 TLS 安装失败**。失败的 Scheme 安装记录保留，另一次新的仅安装检查成功。仅 QEMU 配置了已审阅的 verifier 依赖 profile（`qemu-alpine-ssh-v1`），且已通过；其余 33 题明确保持 `not_configured`。[预检证据](../../configs/dev34-flash1017-main-20261019/preflight-evidence.json)按哈希绑定每份原生记录。Agent 安装成功不代表未配置的 verifier 依赖已通过认证。

原队列中的三项主机作业在任何原生任务试次或模型输出产生前失败：两次 Harbor registry 连接失败和一次构建 wheel 时的 PyPI TLS 请求失败。[原始启动证据](../../configs/dev34-flash1017-main-20261019/launch-failure-evidence.json)保留。三个预登记的单题补启动计划利用原队列最后一对任务空出的执行位串行运行。因此，37 次主机启动产生了 **34 个独立的新 agent 试次**，没有替换任何已生成输出。已根据时间戳核对原队列的成对屏障，以及全局最多两个并发任务作业的限制。

验证共进行 **37 次尝试，其中 3 次是超时重试**。模型恢复题在 pytest 启动前用尽三次 900 秒尝试。流水线并行题第一次在依赖准备阶段达到 900 秒时限，第二次在 427.42 秒内完成并得到有效的计分失败。其余每题均只尝试一次。未启用下载错误重试，未改变逐次时限，也未在执行得到测试结果后重试。

PyTorch 两题运行期间，因磁盘空间紧张，将重复的主机镜像缓存临时迁移到内存临时文件系统。六个 OCI 归档和 44 个内容寻址 blob 均恢复为普通文件，逐个重新核对 SHA256。原始 Docker 镜像及任务环境未被替换。最终检查确认 **34 个原始镜像身份均未改变**，且**没有残留任务容器**。

全部原队列及补启动作业结束后，才审阅新轨迹和官方测试内容。输出冻结记录时间为 `2026-10-19T18:10:43.804209+00:00`。模型阶段占用 **264.23 分钟**，不含仅安装预检。34 份记录的用量和费用信息均完整；随 agent 提供的估算器给出 **$1.861**。这是 token 费用估算，并非账单对账结果。

## 冻结后审计与解释

自动扫描覆盖全部 34 份轨迹和 agent 标准输出日志，随后审阅标记的工具调用、观察结果、外部 URL、失败证据和 verifier 准备错误。未观察到配置的提供商密钥完整匹配、检索任务专用 benchmark 答案，或读取隐藏 verifier 内容。WAL 题检查了空的 verifier 日志目录。张量并行题搜索最近创建的测试，但观察中返回的是已安装依赖的测试。公开 MTEB 结果属于任务要求的数据来源。这些发现不能证明完全没有信息接触或训练污染。

通过的 Scheme 求值器依赖宿主解释器内省：它通过乘法原语的 Python 求值行为，重置宿主求值深度计数器。保留其官方通过分数，同时记录这一实现上的限制。

[10 月 12 日 baseline](dev34-main-baseline-20261012.md)为 28 题通过、6 题计分失败。本轮采样器、KV 存储和 SQL 优化由失败变为通过；WAL、流水线并行和正则棋仍为计分失败。DNA 组装和 POV-Ray 由通过变为计分失败。此前通过的三题变为 verifier 错误未计分。未复用任何此前的输出或分数。

全部 34 题均已有开发暴露。每题单次新试次、在线依赖解析、agent 修改的环境、主机启动恢复，以及变化的提供商条件，都使本轮无法作为隔离 checkpoint 影响的受控比较。三道未计分题单独保留，记录通过的 Scheme 实现限制，逐题证据用于开发分析；不将本轮视为保留集能力分数。
